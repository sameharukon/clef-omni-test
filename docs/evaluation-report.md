# Clef-omni 音声判定 検証レポート

- 対象モデル: `@cf/cloudflare/clef-omni`（Workers AI）
- 検証日: 2026-10-11
- 検証内容: マイクで話した日本語の「右」「左」を Clef-omni で判定し、3 レーンの車ゲームの操作に使えるか

## 1. 結論

- **「左かどうか」を `noul`（yes/no）型で尋ね、左でなければ右とする方式で、右・左とも全問正解（最終回 右 24/24、左 16/16）**。
  右と話したときの `P(左)` は 0.01〜0.06、左では 0.96〜0.98 で、しきい値 0.5 に対して十分な余裕がある。
- 当初の 3 択（右 / 左 / なし）では「左」は安定して判定できたが、**「右（みぎ）」の取りこぼしが多く**（右 7/15、9/21）、実用にならなかった。
- AI 処理時間は中央値 約 130〜240ms。ただし**時間帯によって 1 秒超が 2 割近く発生し、最大 3.7 秒**を観測した。
  ゲーム操作では遅れた結果を反映しない対策が必要。
- 費用は 1 判定あたり約 $0.00004（推定）で、検証用途なら Workers AI の無料枠に収まる。

ただし、**話者 1 名・同一環境・各回 30 件前後**での結果であり、一般化には追加検証が必要（「7. 制約」参照）。

## 2. 検証構成

| 項目 | 内容 |
|---|---|
| 音声取得 | ブラウザの AudioWorklet でマイク入力を取得 |
| 発話区間検出 | 音量しきい値方式。発話前 250ms を含め、無音 350ms で終了、最大 1.5 秒、80ms 未満の音は破棄 |
| 送信形式 | 16kHz / 16bit / モノラル WAV を base64 data URL で Worker に送信。送信前にピーク音量を 0.9 に正規化（最大 10 倍） |
| 判定 | Worker から Clef-omni を呼び出し、結果をブラウザに返す |
| 評価 | 判定ログの各行に正解（右 / 左 / 他）を手動で付与し、正解率などを集計 |

最終的な問い合わせ内容:

```js
{
  model: "clef-omni",
  state: "A short Japanese voice command.",
  audio: ["data:audio/wav;base64,..."],
  questions: {
    direction: {
      type: "noul",
      instructions:
        "Did the speaker say 「左」/「ひだり」 (hidari, left), possibly with 左へ or 左に? " +
        "Answer no for any other word, including 「右」/「みぎ」 (migi, right).",
    },
  },
}
```

## 3. 検証の経過

### 3.1 第 1 回: 3 択（正解ラベルなし、30 件）

- 判定を採用したのは 30 件中 16 件（信頼度の下限 0.5）。
- 信頼度は 0.64〜0.87 と 0.00〜0.04 に二極化し、中間は 2 件のみ。
- AI 処理時間は 105〜170ms が中心。外れ値は 413ms と 830ms（いずれも各セッションの序盤）。

### 3.2 第 2 回: 3 択（正解ラベル付き、28 件）

| 指標 | 値 |
|---|---|
| 正解率 | 57%（16/28） |
| 誤判定 | 0 件 |
| 取りこぼし | 12 件 |
| 内訳 | 右 7/15、左 9/13 |
| モデル判定そのものの正解率（信頼度の下限を無視） | 71% |

- 採用した判定は全て正解。課題は「間違える」ことではなく「聞き取れない」こと。
- 取りこぼした発話は、選択肢の確率がほぼ均等（最大でも 0.37〜0.56）だった。
- `confidence` の算出方法をログから特定した（4.1）。

### 3.3 第 3 回: 3 択 + 信頼度不足時の再送（33 件）

仮説: Clef-omni は音声を約 13 トークン/秒（1 トークン ≒ 77ms）に変換するため、0.3 秒程度の「みぎ」は 4 トークン程度にしかならず、
単語がトークン境界のどこに来るかで判定が不安定になる。

検証: 初回の信頼度が下限未満なら、音声の先頭に 38ms / 19ms の無音を足して並列に再送し、最も信頼度の高い結果を採用。

| 指標 | 値 |
|---|---|
| 正解率 | 64%（21/33） |
| 再送なしの場合の正解率 | 58% |
| 再送 | 14 件 → 採用 2 件（いずれも 38ms ずらし、いずれも正解） |
| 内訳 | **右 9/21、左 12/12** |

- 取りこぼし 12 件は全て「右」。うち 9 件は「なし」の確率が最も高く（0.42〜0.58）、モデルは「何かは聞こえたが右には聞こえない」と判断していた。
- 送信前の増幅率は右が平均 約 3.4 倍、左が 約 2.4 倍で、「みぎ」は「ひだり」より音のエネルギーが小さい。
  ただし右の中では成功時と失敗時で増幅率に差はなかった。
- 再送は追加リクエスト 28 回で 2 件の救済にとどまり、費用対効果が低い。**トークン境界の仮説は主因ではない**と判断。
- 応答が 7 秒以上返らない問い合わせが 1 件発生（タイムアウト未設定だったため「再送中」のまま停止）。

### 3.4 第 4 回: 「左かどうか」を noul 型で判定（28 件）

左は安定して判定できていたため、「左と言ったか」を yes/no で尋ね、左でなければ右とする方式に変更。

| 指標 | 値 |
|---|---|
| 正解率 | 96%（27/28） |
| 内訳 | **右 12/12、左 15/15**、他 0/1 |
| `P(左)` | 右と話したとき 0.03〜0.18、左と話したとき 0.66〜0.98 |
| AI 処理時間 | 中央値 約 240ms、**1 秒超 5/28 件（最大 3,736ms）** |

- 唯一の誤りは雑音（「他」）を右と判定したもので、方式上想定どおり。
- 遅延の悪化が新たな課題に。

### 3.5 第 5 回: プロンプト簡素化 + noul 型と choice 型の比較（41 件）

判断に不要な文脈（「3 レーンのゲームで車を操作する」等）を `state` と質問文から削除。
あわせて、同じ「左かどうか」を choice 型（左 / それ以外の 2 択）で尋ねる方式と、同じ時間帯で交互に比較。

| 方式 | 件数 | 右 | 左 | 右と話したときの `P(左)` | 左と話したときの `P(左)` | AI 処理時間 中央値 | 1 秒超 |
|---|---|---|---|---|---|---|---|
| noul 型 | 21 | 全問正解 | 全問正解 | 0.011〜0.060 | 0.958〜0.985 | 160ms | 0/21 |
| choice 型 | 20 | 全問正解 | 全問正解 | 0.023〜**0.335** | 0.856〜0.973 | 157ms | 0/20 |

（全体: 正解率 98%（40/41）、右 24/24、左 16/16、他 0/1）

- **速度は同等**。第 4 回の遅延は型の違いではなく、時間帯による Workers AI 側の処理待ちと考えられる。
- **noul 型のほうがしきい値 0.5 に対する余裕が大きい**（最小の余裕 約 0.44 対 約 0.17）。noul 型を採用し、choice 型の左判定は削除した。
- noul 型の分離は第 4 回（右 0.03〜0.18、左 0.66〜0.98）より明確になった。プロンプト簡素化の効果の可能性があるが、別セッションのため断定はできない。

## 4. 主な知見

### 4.1 choice 型の `confidence` の意味

`confidence` は選んだ選択肢の確率ではなく、確率分布の偏りを 0〜1 に正規化した値と一致した（選択肢数を k として）。

```
confidence = (Σ pᵢ² − 1/k) / (1 − 1/k)
```

- 例: right 0.9509 / left 0.0256 / none 0.0235 → 0.858（ログの値と一致）
- 例: right 0.2541 / left 0.3954 / none 0.3505 → 0.016（ログの値と一致）

このため、最上位の選択肢が「左」でも信頼度が 0.01 になることがある（＝ほぼ均等で判定不能）。公式ドキュメントでの記載は未確認。

### 4.2 短い単語は選択肢の設計で精度が大きく変わる

- 3 択では「右（みぎ）」の取りこぼしが多かったが、「左かどうか」の二値に変えると右・左とも全問正解になった。
- 判定しやすい単語を基準にした二値判定は、短い音声コマンドに有効な設計といえる。

### 4.3 プロンプトは判定に必要な情報だけでよい

- ゲームの説明などの文脈を削除しても精度は落ちず、分離はむしろ明確になった（効果の大きさは未確定）。

### 4.4 遅延は時間帯によるばらつきが大きい

| 回 | AI 処理時間 中央値 | 1 秒超 |
|---|---|---|
| 第 1 回（3 択） | 約 120ms | 0/30 |
| 第 4 回（noul） | 約 240ms | 5/28（最大 3,736ms） |
| 第 5 回（noul / choice） | 160ms / 157ms | 0/41 |

- 公式の目安（音声入力で 100ms 未満）よりやや遅い。
- 話し終わりから車が動くまでは、無音判定 350ms + 往復 約 150〜250ms で約 0.5〜0.6 秒。体感上は無音判定の待ち時間の影響も大きい。

## 5. 現在の実装（検証結果を受けた対策）

| 項目 | 設定 |
|---|---|
| 判定方式 | 「左かどうか」（noul 型）。`P(左)` ≥ 0.5 なら左、それ以外は右（しきい値は画面で調整可） |
| 3 択 | 比較用に残置。信頼度不足時の再送（38 / 19 / 58ms ずらし）は 3 択のみで有効 |
| 遅れた結果 | 送信から 1000ms（画面で調整可）を超えて返った判定は車に反映しない |
| 順序逆転 | 後の発話の結果を反映済みなら、前の発話の結果は反映しない |
| タイムアウト | 5 秒で問い合わせを打ち切る |
| 評価機能 | 正解ラベル付与、正解率・内訳・判定方式別の AI 処理時間の集計、ログのコピー / CSV 出力 |

## 6. 費用と制限（試算）

| 項目 | 値 |
|---|---|
| 単価 | 入力 100 万トークンあたり $0.15（出力は無課金） |
| 音声のトークン換算 | 約 780 トークン/分（約 13 トークン/秒） |
| 1 判定あたり | 約 200〜300 トークン（音声 約 13〜20、残りは質問文。推定）→ 約 $0.00004 |
| 無料枠 | 1 日 10,000 Neurons（約 73 万トークン、約 2,500〜3,500 判定/日） |
| Workers Paid | 月額 $5 + 無料枠超過分。無料枠を超えた後は $1 あたり約 27,000 判定 |
| レート制限 | テキスト生成系の既定は 1 アカウント・1 モデルあたり毎分 300 リクエスト（1 人が 2 秒ごとに話すと同時 約 10 人が目安） |

1 判定あたりのトークン数は推定値。実際の値はレスポンスの `usage` で確認できる。

## 7. 制約

- 話者は 1 名、マイク・環境も同一。話者・マイク・騒音環境が変わった場合の精度は未検証。
- 各回 20〜41 件と件数が少なく、正解率の差の一部は誤差の範囲の可能性がある。
- 雑音・右左以外の発話（「他」）の試行は各回 1 件のみ。
- 回ごとに方式・プロンプト・時間帯が同時に変わっているものがあり、個々の要因の効果を厳密には分離できていない（第 5 回の noul / choice 比較は同一時間帯で交互に実施）。

## 8. 残課題

1. **雑音対策**: 現方式では雑音や右左以外の発話が必ず「右」になる。同じリクエストに「人の言葉か」を問う noul 質問を追加する案がある。評価には「他」の試行（咳、拍手、別の言葉など）が 10 件程度必要。
2. **遅延の外れ値**: 反映しない対策は入れたが、根本原因（時間帯による処理待ち）は未解決。時間帯を変えた継続計測が必要。
3. **汎化の確認**: 複数話者・複数環境での検証。
4. **代替手段との比較**: 端末内で動く方式（Web Speech API、Vosk の語彙限定、EmbeddingGemma 2 の音声埋め込みなど）と、精度・遅延・費用を比較する余地がある。
